### Fixed

- **Echoed info-hash validated on attached conns (audit A03 round-2,
  wire+state)**: `run_handshake`, `run_handshake_encrypted_initiator`
  and `run_handshake_encrypted_responder_prefix` all re-check the
  remote's echoed info-hash against the conn's
  `associated_info_hash()` — upstream `read_info_hash`'s `else`
  branch (`bt_peer_connection.cpp:3484-3503`), which the round-1
  report wrongly claimed didn't exist for attached conns. A v2 echo
  flips `protocol_v2` and `wire_ih` (the reply then carries the
  truncated v2 hash); any other mismatch disconnects
  `invalid_info_hash` at *failure*; an all-zero echo is refused.
  `peer_link_up` now hands the full `KnownTorrent` (v2 hash +
  `valid_metadata`) to the handshake paths so the check is
  consistent everywhere.

- **`m_encrypted` timing parity — crypto failure counters no longer
  over-counted**: `HandshakeState::encrypted` is set only when the
  MSE negotiation completes (PE4 exchanged, IA consumed) instead of
  at MSE entry — upstream sets `m_encrypted` in
  `init_bt_handshake`/`read_pe_ia`. Pre-PE4 failures (bad sync,
  degenerate DH, `select == 0`, oversized `len_pad`/`len_ia`) no
  longer bump `error_encrypted_peers`/`error_rc4_peers`.

- **PE4 emitted before length rejections (wire)**: the MSE responder
  writes PE4 (`VC + crypto_select + len_pad`) immediately after
  picking the crypto mode — before validating `len_pad`/`len_ia`,
  matching upstream `read_pe_cryptofield` (`write_pe4_sync` at
  :3183 precedes the `invalid_pad_size`/`invalid_encrypt_handshake`
  legs). A malformed initiator now sees our PE4 on the wire before
  the close, exactly like a real libtorrent peer.

- **Post-attach teardown counts crypto legs**: `peer_disconnected`
  now runs the `error_encrypted_peers`/`error_rc4_peers` counter
  legs off the conn's final `supports_encryption()`/`rc4_encrypted()`
  flags when severity > normal (upstream `peer_connection.cpp`
  :4414-4422) — round-1 only covered pre-attach handshake failures.

- **SSL acceptor failure parity**: the BT-handshake legs after a
  successful TLS accept now run the same `disconnect()` accounting
  as the plain acceptor (`peer_conn_failed_inbound` — counters +
  alert, torrent handle when attached), including the
  `handshake_timeout` leg (`timed_out_no_handshake`).

- **DHT secret-id fishing ban on every inbound transport**: an
  inbound info-hash equal to our `generate_secret_id()` value now
  triggers `ban_ip` on the plain socket acceptor and the SSL
  acceptor, not only the injected `accept_stream` path — upstream
  runs the check inside `attach_to_torrent`
  (`peer_connection.cpp:1326-1336`). The ban no longer skips the
  `disconnect(invalid_info_hash)` counter/alert legs upstream runs
  right after it.

- **`accept_stream` handshake bounded**: the injected-transport
  entry point is wrapped in `handshake_timeout` like the socket
  acceptors — a silent peer can no longer pin a `num_peers_half_open`
  conn and its stream forever.

- **Manual `connect_peer` TLS-wraps SSL torrents**: the API dial
  path now resolves `ssl_dial_params` and runs `ssl_connect` with
  the torrent's root/cert/SNI exactly like `spawn_dial` —
  upstream `connect_to_peer` instantiates `ssl_stream` for SSL
  torrents regardless of the dial's origin.
