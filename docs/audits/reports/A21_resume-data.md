## Verdicts checklist

- Champs : pieces bitfield, unfinished, priorities, trackers, peers+banned, seeds_dht, limits, totals, active/seeding time, flags (upload/share/seed/auto_managed/paused/apply_ip_filter), save_path, renamed/mapped_files, file_format_version, ih v2, comment/created_by/creation_date — verdict : **déviation** — preuve : champs lus/écrits exhaustifs et fidèles (`crates/bitdaemon-core/src/resume_data.rs:82-415` read, `:437-685` write ; `torrent.rs:2455-2627` `to_resume_data`), **mais** `have_pieces`/`verified` sont écrits sans la gate `max_piece` upstream (`src/torrent.cpp:7624-7650`) et `piece_priority` sans la gate `!default_prio` (:7731-7749) — cf. Déviations 1 et 7. `seeds_dht` n'existe pas dans le format resume upstream (N-A ; `dht_nodes` ne transite que par `write_torrent_file`).
- verify_resume_data verdicts : no_resume/need_full_check, fichiers manquants/modifiés/tailles, `partial` — verdict : **déviation** — preuve : `verify_resume_data` fidèle (`bitdaemon-disk/src/storage_utils.rs:683-812`), `check_fastresume` job fidèle (`disk_io.rs:1398-1460`), mais le masque `rejected` de la session omet `FILE_EXIST` (`session.rs:2711-2714` vs upstream `has_error_status` à `torrent.cpp:2307-2310`), et la branche « bitfield partiel → reprise du check à `end_index` » (`torrent.cpp:2335-2344`) n'a pas d'équivalent — cf. Déviations 3 et 5.
- Snapshot sous I/O : dirty cache blocks cohérents avec le disque post-reload — écritures en vol + fences pendant write_resume_data — verdict : **déviation** — preuve : `unfinished` snapshotte bien `finished || writing` avec masque `Finished`-only comme upstream (`torrent.rs:2614-2625` vs `torrent.cpp:7579-7605`), et `have` reflète des pièces hashées donc flushées (repost des hash jobs derrière les writes, `disk_io.rs:1465`), **mais** pendant `checking_resume_data`/`checking_files` `self.have` est écrit tel quel (claims non vérifiés / check partiel en clair) au lieu d'être vidé ou tronqué à `num_checked` — cf. Déviation 1.
- Round-trip BIDIRECTIONNEL : fichier upstream → lu ici ; écrit ici → lu par upstream (golden vectors) — verdict : **déviation (partielle)** — preuve : format file-version 1 et 2 lus (`resume_data.rs:102-105, 326-345` ; v1 `pieces` 1 byte/pièce bit0=have bit1=verified, v1 `verified`/`mask` chaînes '0'/'1'), tests `tests/test_resume.rs` couvrent `to_resume_data`/`apply_resume_data` mais **aucun golden vector généré depuis C++** : pas de fixture `.resume` upstream dans `crates/*/tests/data/`. Le sens écrit-ici→lu-upstream n'est pas démontré (les déviations 1/7 produisent des clés qu'upstream n'émet pas — `pieces` plein-format tout-à-zéro change le verdict `contains_resume_data` côté lecteur).
- Versions : upgrade/downgrade du format resume entre versions libtorrent — verdict : **conforme** — preuve : `file-version` ∈ {1,2} accepté, autres rejetés `InvalidFileTag` (`resume_data.rs:102-105`) ; chemins v1 (`pieces` octets, `trees` verified/mask en '0'/'1') et v2 (bitfields binaires bornés `piece_limit`) implémentés (`resume_data.rs:174-207, 326-345`) ; écriture toujours `file-version=2` (`:450`) comme upstream.
- save_resume_data timing : dirty flags, déclencheurs `need_save_resume` exhaustifs — verdict : **déviation** — preuve : marquage `need_save_resume` très couvrant (~40 sites `torrent.rs`), `only_if_modified` → `SaveResumeDataFailed` comme upstream `resume_data_not_modified` (`session.rs:9842-9848`), tick périodique `save_resume_data_interval` (`session.rs:9859-9874`) ; **mais** le flag est sali par l'application du resume et par le verdict (`apply_resume_data` `torrent.rs:2710`, `on_files_checked` `torrent.rs:2971`) alors qu'upstream préserve `m_need_save_resume_data` de part en part (`torrent.cpp:2244, 2474-2476`), il manque l'alerte `torrent_removed` quand le torrent est aborté (`session.rs:9834` retour silencieux vs `torrent.cpp:10096-10101`), et les flags `flush_disk_cache`/`save_info_dict`/conditions granulaires `if_*` sont aplatis en un bool — cf. Déviations 6 et 8.

## Déviations

- `crates/bitdaemon-session/src/torrent.rs:2476` — `to_resume_data` écrit `atp.have_pieces = self.have.clone()` sans condition ; upstream (`src/torrent.cpp:7624-7650`) calcule `max_piece = is_checking ? m_num_checked_pieces : m_files_checked ? end_piece : 0` — **rien** n'est écrit tant que `!m_files_checked`, et pendant `checking_files` seules les pièces vérifiées sont persistées (bitfield *partiel* `resize(max_piece)`). Conséquences : (a) un torrent jamais checké émet une clé `pieces` plein-format tout-à-zéro → `contains_resume_data` vrai au reload (`!empty`, `add_torrent_params.cpp:39` ; `disk_io.rs:1434` teste `size() > 0`) → on saute la jambe `has_any_file → need_full_check` → des données complètes sur disque sont ignorées au lieu d'être re-vérifiées ; (b) pendant `checking_resume_data`, la *claim* non vérifiée est persistée ; (c) un snapshot en cours de `checking_files` ne permet jamais la reprise-de-check (bitfield jamais partiel). Sévérité : **état → données** (re-download au lieu de recheck ; claims non vérifiées persistées).
  - **sketch** : dans `to_resume_data`, remplacer la copie par la gate upstream :
    ```rust
    // upstream torrent.cpp:7631 max_piece
    let max_piece = if self.state == TorrentState::CheckingFiles && !self.checking_resume {
        self.num_pieces - self.checking_pieces   // pieces hashed so far
    } else if self.files_checked {
        self.num_pieces
    } else {
        0
    };
    if max_piece > 0 {
        let mut h = Bitfield::with_size(max_piece as usize);
        if self.is_seed() { h.set_all(); }
        else {
            for i in 0..max_piece {
                if self.have.get_bit(i as usize) { h.set_bit(i as usize); }
            }
        }
        atp.have_pieces = h;
        if self.seed_mode { atp.verified_pieces = self.seed_verified.clone(); }
    }
    ```
    (upstream `checking_files` exclut `checking_resume_data` — `state() == checking_files` seulement ; chez nous `checking_resume` distingue les deux). Déplacer le bloc `verified` (l.2478-2480) **à l'intérieur** du `max_piece > 0` comme upstream. Test : `to_resume_data` sur torrent `files_checked=false` → `atp.have_pieces.is_empty()` ; torrent mid-check → `pieces.size() < num_pieces`.

- `crates/bitdaemon-session/src/torrent.rs:2711-2735` + `:3010-3023` — `apply_resume_data` applique `unfinished_pieces` (marque les blocs `Finished` dans le picker) **avant** le verdict ; upstream n'applique `unfinished` que dans la branche acceptée de `on_resume_data_checked` (`torrent.cpp:2366-2404`). Sur rejet, `on_files_checked(false)` ne défait que `have`/`verified_bytes` — les blocs fantômes restent `Finished` dans le picker (la pièce peut même partir en `DiskHash` via `is_piece_finished` — ou pas — puis rester marquée). Le rejet n'éteint pas non plus `seed_mode` (upstream `m_seed_mode = false` dans la branche `has_error_status`, `torrent.cpp:2408`). Sévérité : **état** (picker incohérent post-rejet ; seed_mode survivant sans pièces).
  - **sketch** : (a) stocker `unfinished_pieces` en attente (p. ex. `self.pending_unfinished: BTreeMap<i32, Bitfield>`) au lieu de les appliquer dans `apply_resume_data` ; appliquer la boucle `mark_as_finished`/`is_piece_finished→DiskHash` dans `on_files_checked(accepted=true)` après la boucle `claimed` — réf. `torrent.cpp:2366-2404` ; (b) dans le bras `!accepted` : `self.seed_mode = false;` avant le `return` (l.3010-3022) — et le `verified_bytes`/picker déjà nettoyés suffisent puisque `unfinished` n'aura jamais été appliqué. - `crates/bitdaemon-session/src/session.rs:2711-2714` — `rejected` masque `NEED_FULL_CHECK | FATAL_DISK_ERROR` ; upstream `has_error_status` inclut aussi `disk_status::file_exist` (`torrent.cpp:2307-2310` : `fatal_disk_error | need_full_check | file_exist`). ## Non-bugs tranchés

- `peers`/`banned_peers` appliqués au *ctor* (`torrent.rs:1326-1345`) plutôt que dans `on_resume_data_checked` : les deux chemins upstream existent (le ctor alimente `m_peer_list` aussi ; le passage post-check couvre les mêmes champs + `update_want_peers`). Timing différent, effet net identique — les peers du resume rejoignent le connect pump dans les deux cas.
- `info` dict : chez nous `atp.ti` est attaché dès que `metadata_raw` existe (`torrent.rs:2585-2596`) ; upstream exige `flags & save_info_dict` (`torrent.cpp:7567`). Comme `save_info_dict` est le flag de fait du chemin `save_resume_data` upstream, l'émission inconditionnelle est sémantiquement équivalente — à documenter si un appelant veut le resume « mince » un jour.
- `to_resume_data` n'écrit pas `atp.dht_nodes` (upstream : `torrent.cpp:7611-7612`) : le champ `nodes` n'entre que dans `write_torrent_file(include_dht_nodes)`, jamais dans le dict resume — hors périmètre réel.
- `libtorrent-version` = `crate::VERSION_STR` (BitDaemon) et non "libtorrent/x.y" : champ informatif ignoré à la lecture — écart volontaire.
- Ordre des clés du dict : `Dictionary` (BTree) tri byte-lexicographique — conforme bencode ; upstream `entry::dict` aussi ordonné.
- `verified`/`mask` des `trees` en file-version 1 : format '0'/'1' géré — conforme (`resume_data.rs:174-207`).
- Caps `bitfield_from_resume` : les triples `(bit_limit, piece_limit)` Rust reproduisent exactement les `piece_limit`/`piece_limit*2`/`INT_MAX` upstream (`resume_data.rs:34-40, 183-207, 344-350, 407`).
